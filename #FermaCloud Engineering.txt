RoadSense Nigeria — Final Workflow
Predictive Road Degradation & Budget Optimisation Engine
Project type: Cloud engineering + data science portfolio project
Sector: Infrastructure / Transportation (FERMA-aligned)
Core engineering challenge: Build a predictive system that forecasts road segment failure using free satellite imagery, open geospatial data, and survival analysis, then optimises maintenance budget allocation across Nigeria's federal road network.
Budget target: $0/month recurring across all tiers
Document type: Workflow specification with tiered tool options (no code)

1. Project Vision
Nigeria's federal road network spans over 36,000 km. FERMA has been directed to build a geo-referenced national database of failed roads, but no public system exists that predicts which roads will fail next or where every naira should be spent. RoadSense fills that gap.

The system ingests satellite imagery, weather data, and open road network data, engineers degradation features over a 24-month window, trains survival models that predict time-to-failure per segment, and optimises maintenance budget allocation using linear programming. Every layer runs on free-tier infrastructure, with at least three alternative tool options per tier so the stack can be swapped without rewriting the project.

2. Architecture Overview
The workflow has nine layers, each producing artefacts consumed by the next. Every layer offers multiple free-tier options, and the system is designed so that any layer can be replaced without breaking the pipeline.

4. Layer 2 — Ingestion (Tiered Options)
The ingestion layer pulls data from source APIs on a weekly schedule. Three implementation paths, each free.

Option A — AWS Lambda Container Images (Serverless, Event-Driven)
Free tier: 1M requests + 400K GB-seconds/month (Always Free)
Why: Container images support GDAL, rasterio, pyproj, and other native geospatial libraries that cannot be packaged in standard Lambda ZIP layers. Geospatial Docker base images are publicly available and Lambda-ready.
Use when: You want a pure AWS serverless narrative with no servers to manage.

Option B — GitHub Actions Scheduled Workflows (Zero-Infrastructure)
Free tier: 2,000 minutes/month for public repos (permanent)
Why: No cloud account needed for compute. The workflow runs on GitHub's runners, pulls data, and pushes results to S3/R2/Supabase. The entire ingestion pipeline lives in version control alongside the code.
Use when: You want the simplest possible setup and want to demonstrate CI/CD-native data engineering.

Option C — Cloudflare Workers + Cron Triggers (Edge-Native)
Free tier: 100,000 requests/day (permanent)
Why: Runs at the edge, near the data. Cloudflare Workers can fetch from APIs, process JSON, and write to R2 or D1 with no cold starts. Cron triggers handle scheduling natively.
Use when: You want to demonstrate edge computing and multi-cloud awareness.

Option D — Databricks Free Edition Lakeflow Connect (Zero-ETL)
Free tier: 100 DBUs/day per workspace (~100M records/day ingestion capacity)
Why: Databricks Free Edition provides a full lakehouse workspace with no credit card, no fixed expiry, and native ingestion connectors. Lakeflow Connect handles incremental syncs without writing ingestion code.
Use when: You want the modern data stack narrative with zero infrastructure management.

9.3 Model Family Comparison
Model Family	Library	When to Use	RoadSense Fit
Cox Proportional Hazards	lifelines, scikit-survival, R survival	Baseline model. Interpretable hazard ratios. Works when proportional hazards assumption holds.	✅ Strong baseline

9.4 Recommended Modelling Strategy
Phase 1 — Baseline: Fit a Cox Proportional Hazards model with lifelines. Test proportional hazards assumption using Schoenfeld residuals. Report concordance index and hazard ratios.

Phase 2 — Regularised: Fit a Cox model with elastic net penalty using scikit-survival's Coxnet. Use cross-validation to tune the penalty. This handles feature selection automatically.

Phase 3 — Non-Linear: Fit a Random Survival Forest and a Gradient Boosting Survival model using scikit-survival. Compare concordance index against the Cox baseline. Expect a 3–8% improvement.

Phase 4 — Ensemble: Stack the best Cox, RSF, and GBSA models using a simple weighted average or a meta-learner. Report ensemble performance.

Phase 5 — Uncertainty: Fit a BART-Survival model on the best feature set. Use the posterior distribution to generate confidence intervals on failure probabilities.

Phase 6 — Validation: Evaluate all models on a temporal holdout set (train on 2022–2024, validate on 2025–2026). Report:

Concordance index (C-index)

Integrated Brier Score (IBS)

Time-dependent AUC at 6, 12, and 24 months

Calibration curves (predicted vs. observed failure rates)

Top-decile capture rate (percentage of observed failures in top 10% of predicted-risk segments)

10. Layer 8 — Budget Optimisation
The optimisation layer takes predicted failure probabilities and repair costs and solves a linear program that maximises expected value preserved subject to a budget constraint. This is a 0/1 knapsack problem.

Free-Tier Options
Tool	Type	Free Tier	Why
PuLP	Python linear programming	Open-source	Simple API, CBC solver bundled, handles knapsack naturally
OR-Tools	Google optimisation suite	Open-source	More powerful than PuLP. Supports CP-SAT, routing, and linear programming.
scipy.optimize	Scientific computing	Open-source	linprog handles linear programs; milp handles mixed-integer problems
CVXPY	Convex optimisation	Open-source	Expressive modelling language. Solver-agnostic.
Google Sheets Solver	Spreadsheet optimisation	Free	For a prototype, a spreadsheet solver demonstrates the concept without code
Optimisation Workflow
Input: Predicted failure probability per segment, repair cost per segment, traffic volume × length as value proxy.

Formulate: Maximise total expected value preserved subject to total cost ≤ budget.

Solve: Use PuLP or OR-Tools to find the optimal subset.

Compare: Report the optimiser's allocation vs. uniform allocation. Calculate the improvement multiplier.

Sensitivity: Run the optimiser across a range of budgets (₦10B, ₦25B, ₦50B, ₦100B) and report the marginal value of each additional naira.

Output Metrics
Metric	Description
Selected segments	List of segment IDs with predicted risk and repair cost
Total cost	Sum of repair costs for selected segments
Expected value preserved	Sum of (failure probability × value) for selected segments
Improvement multiplier	Value preserved by optimiser ÷ value preserved by uniform allocation
Marginal value of budget	How much additional value is preserved per additional ₦1B

12. End-to-End Workflow
Stage 1 — Weekly Satellite Ingestion
Satellite imagery is pulled from Copernicus Data Space Ecosystem via the STAC API. Only the Red and NIR bands are read for a 100m buffer around each road segment using cloud-optimised GeoTIFF range requests. NDVI and NDBI are computed per segment per observation. Results are written to the storage layer.

Stage 2 — Weekly Weather Ingestion
Open-Meteo Historical API is queried once per 1° × 1° grid cell (approximately 150 cells covering Nigeria). Daily rainfall, temperature extremes, and soil moisture are retrieved for the past 7 days and appended to the weather time series.

Stage 3 — Monthly Road Network Refresh
GRID3 NGA Roads FeatureServer is queried per spatial tile for motorway, trunk, primary, and secondary roads. Each segment is written with geometry, class, surface, speed estimate, and geohash. The full refresh covers approximately 150,000–200,000 segments.

Stage 4 — Monthly Label Extraction
FERMA project completion records are scraped from the procurement portal, Federal Ministry of Information press releases, and news archives. Road names are fuzzy-matched against GRID3 segments and written as failure events with completion dates and event types.

Stage 5 — Weekly Feature Engineering
For each road segment, the system computes 24-month rolling features: NDVI mean/trend/variance, NDBI mean/trend/variance, cumulative rainfall, max 7-day rainfall, dry spell count, temperature range, soil moisture saturation events, road class, surface type, segment length, speed estimate, settlement proximity, and time since last FERMA intervention. Features are written to the feature store and exported to Parquet.

Stage 6 — Weekly Model Training
The training pipeline runs on GitHub Actions (2,000 free minutes/month). It pulls the latest features and labels, fits multiple survival models (Cox PH, Coxnet, RSF, GBSA, BART-Survival), evaluates each on a temporal holdout set, and selects the best performer by concordance index. The model is serialised and a model card is written with C-index, calibration metrics, and top hazard ratios.

Stage 7 — Weekly Optimisation
Predicted failure probabilities and repair costs are fed into a linear program. The optimiser selects the subset of segments that maximises expected value preserved subject to the annual budget. Results are written to the serving layer.

Stage 8 — Continuous Serving
The dashboard displays a risk heatmap of federal roads, ranked by predicted failure probability. Users can click a segment to see its NDVI trend, rainfall history, and predicted survival curve. A budget simulator lets users adjust the budget and see live updates of selected segments and expected value preserved.

14. Risks & Mitigations
Risk	Impact	Mitigation
Sparse FERMA label data	Model cannot train	Supplement with news reports and procurement records; use censored data
Fuzzy matching errors	Wrong segments labelled	Confidence threshold + manual review queue
GRID3 road network gaps	Segments missing	Accept 5–10% gap; document in README
Sentinel-2 cloud cover	Missing observations	Multi-temporal compositing; cloud masking via L2A
Cox PH assumption violation	Underestimated risk	Test Schoenfeld residuals; use time-varying covariates or RSF/GBSA
GitHub Actions minutes exhausted	Pipeline stops	Daily runs take <5 minutes; 2,000 minutes/month is ample
S3 GET request overrun	Unexpected charges	Use Cloudflare R2 instead; monitor weekly
Dashboard cold start	Slow UX	Cloudflare Workers have no cold starts

16. Positioning Statement
RoadSense Nigeria is a cloud engineering and data science project that predicts road segment failure using free satellite imagery, open geospatial data, and survival analysis, then optimises maintenance budget allocation across Nigeria's federal road network. It demonstrates remote sensing, feature engineering at scale, survival modelling across seven model families, linear programming, modern data orchestration, feature stores, and serverless serving — all running on permanent free tiers at zero recurring cost. The project directly answers the Federal Government's 2026 directive for FERMA to develop a geo-referenced national database of failed roads, and goes further by predicting which roads will fail next and where every naira should be spent.
